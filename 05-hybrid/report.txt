REPORT
1. IMPLEMENTATION

Decomposition:
The partition() function divides the grid horizontally among MPI ranks.
Rank r receives N/P + (r < N%P) rows, where P is the number of ranks.
Remaining rows go to the first ranks to balance the workload. Each rank
allocates two local grids (current and next) with two extra halo rows.
Configurations with more ranks than rows are rejected.

Example: N = 10, P = 3 (numbers represent global row indices).

Rank   Top halo   Owned rows    Bottom halo
0      zero       [0 1 2 3]     4
1      3          [4 5 6]       7
2      6          [7 8 9]       zero

counts = {4, 3, 3}
starts = {0, 4, 7}

Initialization:
Each rank initializes its own cells with the supplied initial_cell()
function using global coordinates (first + i, col). OpenMP parallelizes
initialization, and the initial grid remains identical to the reference.

Communication:
Before each generation, exchange_halos() uses two MPI_Sendrecv() calls
to exchange boundary rows with neighbouring ranks. MPI_PROC_NULL is used
for missing neighbours, so the external halo rows remain zero.

Synchronization:
The evolve() function parallelizes the outer row loop with OpenMP and
static scheduling. The final implementation uses shared with explicit
local copies of current, next, n and width (cur, nxt, cols and w) at
the beginning of each row. Only pointer values and scalar parameters
are copied; the underlying grids remain shared within each rank.
Initialization also uses shared. Plain shared and firstprivate variants
were tested for comparison.

Double buffering separates reads from writes, and the implicit barrier
ensures all threads finish before the buffers are swapped.
MPI_THREAD_FUNNELED is used because only the initializing thread of
each rank calls MPI functions.

Population counting:
OpenMP reduction combines thread-local counts. MPI_Reduce with MPI_SUM
combines the local totals on rank 0, which prints the global population.

Final-image export:
The export_grid() function uses MPI_Gatherv() to collect owned cells,
excluding halos, on rank 0. Variable counts and displacements support
uneven partitions. The supplied save_pbm() function writes the image.


2. VALIDATION

The hybrid implementation was compared against the provided sequential
reference using both standard output and the final PBM image. The 15
recorded tests cover grid sizes from 1 to 2048, different step counts,
MPI ranks and OpenMP thread counts.

The tests include minimal grids, zero generations, uneven partitions,
one owned row per MPI rank and larger grids. These cases exercise
initialization, boundary handling, halo exchange, local computation,
population reductions and the final gather.

All 15 recorded configurations matched both outputs. Population counts
check the total number of living cells at each step, while the final-grid
comparison also checks their exact positions. For zero steps, the output
is the initial grid and no population lines are printed.

The original 15-test table does not identify the OpenMP variant used.
The local-copy variant also matched the serial output in the recorded
performance and interleaved experiments (sections 3.1 and 3.5).

Fixed N and step count:
N = 4096, steps = 200.

Timing method and precision:
Three runs per configuration. Median wall-clock time reported to 0.01 s.

Scope:
Whole-program wall time, including computation, communication, output
and MPI startup/exit.

Resource count used for parallel efficiency:
Requested workers = MPI ranks * OpenMP threads per rank.
Speedup = serial median time / parallel median time.
Efficiency (%) = 100 * speedup / requested workers.

Each series uses its own sequential baseline. Medians, speedup and
efficiency are calculated from the recorded run times, with speedup
rounded to two decimals and efficiency to the nearest integer percent.
Efficiency is calculated before rounding speedup.

4. SHORT DISCUSSION

Scaling:
The hybrid implementation with one rank and one thread is slower than
the sequential reference in all five series, consistent with additional
MPI and OpenMP overhead without the benefit of parallel computation.
Increasing the worker count generally improves performance. The best
tested layout in every series was 4 MPI ranks with 2 threads per rank.

Layouts with the same number of workers can perform differently. On
the MacBook Pro using firstprivate, the 4 x 2, 2 x 4 and 8 x 1 layouts
took 1.66 s, 1.86 s and 2.79 s, respectively. More MPI ranks introduce
more partition boundaries and halo communication, whereas OpenMP
threads share the local grids within each rank. Communication,
synchronization, memory bandwidth and runtime overhead may limit
speedup, but their individual costs were not measured separately.

Comparison of OpenMP variants:
The firstprivate version was faster than plain shared in all eight
parallel layouts on the MacBook Air and seven of eight on the Pro.
For the best layout, execution time decreased from 2.96 to 2.20 s
on the Air (25.7%) and from 1.97 to 1.66 s on the Pro (15.7%).
The exception was 8 ranks with 1 thread on the Pro (2.77 to 2.79 s).
The run-time ranges overlap, so this small difference is inconclusive.

The generated LLVM IR provides a possible explanation for the
improvement. In the shared version, captured variables are passed by
reference. Because unsigned char pointers may alias other objects,
conservative alias analysis can limit the compiler's ability to keep
captured values in registers. The shared loop contains 35 static load
instructions, 11 directly from captured-variable arguments, compared
with 15 and 0 in the firstprivate loop.

The final implementation retains shared but creates local copies of
current, next, n and width at the beginning of each row. Its compiled
loop contains 22 load instructions, including 6 directly from captured
arguments. On the Air, this version achieved performance comparable
to firstprivate, with median differences of at most 0.15 s in the
original runs and 0.21 s in the interleaved runs. For the best layout
in the interleaved experiment, plain shared took 2.89 s, local copies
2.17 s and firstprivate 2.16 s.

These observations support the compiler-optimization explanation, but
static IR counts do not measure executed instructions or establish
the exact cause of the whole-program timing differences. The local-copy
version was tested on the Air only. The sequential baselines also varied
between series, so small timing differences should not be overinterpreted.

Hardware comparison:
The Pro was faster in all shared layouts and seven of eight
firstprivate parallel layouts. For the best layout, the Air/Pro time
ratio was 1.50 with shared and 1.33 with firstprivate.

Despite the difference in hardware resources, sequential and one- or
two-worker configurations differed by only 0.08 to 0.36 s. Both CPUs
belong to the M4 generation, and these layouts may not fully utilize
the Pro's additional performance cores (10 compared with 4 on the Air).
The Pro's advantage is more noticeable in several eight-worker layouts.

The relatively short execution times and whole-program overhead may
also limit the observable hardware advantage. Only one problem size
was tested, so a larger performance gap for larger workloads remains
a hypothesis rather than an established result.

Limitations:
All experiments used one node, one performance problem size and
three timed runs per configuration. Multi-node scalability was not
evaluated, and actual rank binding and thread affinity were not
recorded. Whole-program timing includes file output and MPI startup
and exit, so computation and communication costs cannot be isolated.
The LLVM IR analysis is specific to the tested Apple Clang compiler.
Larger workloads and more worker configurations could help assess
the hardware advantage more fully.

Overall, the best measured result was 1.66 s on the MacBook Pro using
firstprivate with 4 MPI ranks and 2 threads per rank (3.54 speedup,
44% efficiency). The final shared-with-local-copies implementation
achieved 2.23 s on the MacBook Air in the main benchmark series
(2.76 speedup, 35% efficiency), comparable to firstprivate.
